**Status:** planned · **Depends on:** Phase 5 (loop architecture); pairs with
Phases 6–8 (9.2 before Phase 8's longest runs; 9.5 helps all) ·
**Read first:** [Phase5.md](Phase5.md) §0 · [styleguide.md](styleguide.md)

---

## 1. Introduction — what this phase delivers

The phases so far add capability; this one adds **stamina**. The v1 audit's
top limitations — session-only chats, hard context dead-ends, one model for
everything, no streaming, no stuck-model economics — all land here. None of
it is glamorous; all of it decides whether a 40-round build session survives.

Concretely:

1. **Streaming** — `fetch` + `getReader()` on `chat/completions`
   (`stream_options: {include_usage}`), live text in the chat, Stop honored
   mid-stream. (Zero existing streaming code in the repo — net-new, as
   planned in `report.md` §6 Phase 4.)
2. **Context compaction** — at ~75% window: summarize the oldest half of the
   transcript through the user's own endpoint, keep a preserved block
   (design intent, open problems, object map, loaded skills, latest
   screenshots' *text* siblings), drop old tool outputs and **all old
   images** first. The `byok-context-full` dead-end becomes a recoverable
   event.
3. **Durable chat history** — `ByokChatStore` moves to IndexedDB (transcripts
   with images exceed localStorage appetite); real archive (not delete); a
   BYOK history list in the chat UI (the server-backed `AskAiHistory` stays
   untouched).
4. **Multi-model routing + per-chat overrides** — model profiles
   (fast/strong), routing policy (fast for scout/summary/compaction calls,
   strong for edits/generation — the sub-agent economics pattern), per-chat
   model & effort override, advanced fields (`temperature`, `max_tokens`).
5. **Capability gating + built-in mini-benchmark** — probe and remember what
   the endpoint supports (vision, `strict` schemas, `parallel_tool_calls`,
   `reasoning_effort`, streaming); a 4-task built-in benchmark so users can
   see which of their models actually builds GDevelop games well (model
   quality dominates every other design choice — SOTA finding).
6. **Local suggestions & feedback** — follow-up suggestion chips generated by
   the user's endpoint (parity with hosted UX); thumbs up/down stored locally
   as a prompt-iteration signal.
7. **Retry/robustness polish** — remember the degraded `reasoning_effort`
   state per model (stop re-400-ing every turn), honor `Retry-After`,
   per-request timeout override for long-reasoning models, mid-run snapshot
   refresh (per-turn `getProjectUserContent` re-read — finishing what Phase
   5's getters started).
8. **Dev-only eval harness** — a fixture suite of ~30 real game tasks with
   reference-outcome scoring, run on demand against any configured endpoint;
   the instrument that tells us whether prompt/skill/tool changes actually
   help (eval-driven tool development is the single most-repeated SOTA
   practice).

## 2. Steps

### Step 9.1 — Streaming (`ByokStreamingClient.js`)

**Goal:** visible progress on long turns; no more frozen-feeling loops.

**How to implement:**

1. `fetch` + `response.body.getReader()`, parse `data: {…}` SSE chunks;
   accumulate `delta.content` into a live transcript item (a growing
   `output_text` item updated through `onAiRequestUpdated` — the chat UI
   already re-renders on store updates); tool-call deltas accumulate until
   `finish_reason`, then flow through the existing pipeline unchanged.
2. `stream_options: {include_usage}` where supported (capability-gated,
   9.5); if the endpoint rejects streaming (probe or first 4xx), fall back
   silently to the non-streaming call and remember per model.
3. Usage accounting: prefer the streamed `usage`; when absent, estimate
   (chars/4) and mark `estimated: true` in the tracker.
4. Stop/suspend: abort the reader (`AbortController`); partial text is kept
   and marked interrupted (mirrors the hosted behavior of truncated turns).

**Tests:** SSE parser on fixture chunks (text, tool-call accumulation, usage,
[DONE]); abort keeps partials; fallback path chosen on stream-rejecting fake.
**Depends on:** Phase 5.

---

### Step 9.2 — Compaction (`ByokCompactor.js`)

**Goal:** long builds survive the window. **Build this before Phase 8's
flagship long runs.**

**How to implement:**

1. Trigger at `contextUsedRatio ≥ 0.75` (before the model call, not after):
   compact, then proceed. Never trigger mid-tool-batch.
2. Preserved block (rebuilt each compaction from explicit sources, never
   from the model's memory of itself): the chat's project-notes entry
   (Phase 7 tool — the durable design intent), current plan (latest
   `create_or_update_plan` payload), open problems (parse from recent
   failed-tool outputs), object/scene map (a fresh `getSimplifiedProject`
   slice), loaded skills list (bodies reload on demand), latest tool
   verification summary.
3. Drop order (SOTA guidance: redundant tool payloads first, images most
   expensive): (1) all images except the latest one; (2) tool outputs older
   than the last 6 turns → replaced by one-line summaries; (3) user/assistant
   turns older than the last 10 → summarized by **one** extra chat-completions
   call (router picks the fast profile, 9.4) into ≤ 600 tokens.
4. The compacted prefix renders as a single "Context summarized" row in the
   chat UI (transcript item type local to BYOK); `byok-context-full` remains
   only as the guard of last resort when even compaction can't fit (e.g.
   window < 8k).

**Tests:** trigger threshold; preserved block contents sourced correctly;
drop order honored (images first); summarizer call mocked, its output capped;
post-compaction request shrinks (message count/chars asserted); last-resort
error still reachable.
**Depends on:** Phase 5 (loop seam), 9.4 (router) if landed first, else
summarizer uses the main model.

---

### Step 9.3 — Durable history (`ByokChatPersistence.js`)

**Goal:** chats survive restarts; archive means archive.

**How to implement:**

1. Small raw-IndexedDB wrapper (no deps): one object store
   `{id → serialized chat record}`; images stored as separate entries keyed
   `chatId:itemId` (records stay lean; transcript references image ids —
   the Phase 6 storage split pays off here).
2. `ByokChatStore` delegates through a persistence interface;
   `BYOK_CHAT_PERSISTENCE_ENABLED` flips to `true`; load-on-open is lazy per
   chat (the list view loads metadata only). Corruption quarantine: a record
   that fails shape validation moves aside, never blocks the store.
3. Real archive: `archivedAt` set, excluded from the default list, restorable;
   delete is explicit and separate.
4. History UI: a BYOK section in the chat header's history popover (new
   small component in `Byok\`, not a modification of server-backed
   `AskAiHistory.js`); rename/archive/delete/open actions mirror it.
5. Storage quota: cap total (e.g. 200 MB) with oldest-chats-first eviction of
   *image entries* before any transcript text is lost; a visible usage line
   in settings.

**Tests:** round-trip (create → reload → identical record); quarantine;
archive/restore; quota eviction order; lazy loading never pulls images for
the list.
**Depends on:** Phase 6 (image storage split), Phase 5.

---

### Step 9.4 — Model routing + per-chat overrides (`ByokModelRouter.js`)

**Goal:** cheap reads, strong writes; user stays in control.

**How to implement:**

1. Settings: model **profiles** — `fast` and `strong` (each = model id +
   optional effort/temperature/max_tokens; default both = current
   `modelName`). Per-chat override UI in the chat header (model + effort
   dropdowns, Phase 4's deferred nice-to-have) — read at turn time, not
   chat-creation time (the getters pattern from Phase 5).
2. Routing policy (a pure function): edits/generation/event-writing →
   `strong`; scout sub-agents, compaction summaries, suggestion chips,
   docs/reference summarization → `fast`. Expose "route automatically" vs
   "always use strong" toggle (users on a single local model are unaffected).
3. Advanced fields per profile: `temperature` (default unset = provider
   default), `max_tokens` (default unset; recommended in help text for small
   local models). These flow through `ByokClient` only when set.

**Tests:** policy truth table (call-kind → profile); overrides beat policy;
unset advanced fields omitted from the request body.
**Depends on:** Phase 5 getters, Phase 8 (sub-agent call kinds) — policy
ships with the call-kinds that exist at land time.

---

### Step 9.5 — Capability probing + built-in benchmark

**Goal:** no more per-turn 400-dance; users can pick models with evidence.

**How to implement:**

1. `ByokCapabilities.js`: per (endpoint, model) cache in settings:
   - `images` (9.0's auto result, remembered),
   - `streaming` (9.1 fallback result),
   - `reasoning_effort` (remembered degraded state — fixes the audit's
     repeated-400 finding),
   - `strictSchemas`, `parallelToolCalls` (probed lazily on first relevant
     feature use; failures degrade: strict off → validated client-side as
     today; parallel off → `parallel_tool_calls: false` sent).
2. `ByokBenchmark.js` — "Test this model (≈2 min)" button in settings: runs
   4 fixed tasks (create scene+objects; write a working event batch via
   EventScript; fix a deliberately broken event sheet; interpret a fixture
   screenshot if vision on) each scored mechanically (project diff vs
   reference / parse success / assertion), and reports
   pass-count + token cost + rounds used. Results stored per model and shown
   next to the model dropdown. All fixtures ship in `Byok\` (no network).
3. Benchmarks use a scratch in-memory project (never the user's).

**Tests:** capability cache semantics; degradation paths; benchmark scorer
against hand-broken fixture outputs (pass/fail/parse-error each direction).
**Depends on:** Phase 5 (executor), Phase 6 (image fixture).

---

### Step 9.6 — Local suggestions & feedback

**Goal:** hosted-loop UX polish, BYOK-owned.

**How to implement:**

1. `ByokSuggestions.js`: after a chat goes `ready`, one `fast`-profile call
   ("suggest 3 short follow-ups given this transcript tail") → chips through
   the existing `message.suggestions` rendering (server chats already show
   them; BYOK transcript items simply start carrying the field). Off by
   default behind a settings toggle (token spend is the user's).
2. Feedback: thumbs up/down on BYOK messages store `{chatId, messageId,
   rating, timestamp}` locally (capped 500) — a settings "export feedback
   JSON" button exists for prompt iteration; nothing is sent anywhere.

**Tests:** suggestion shape matches the UI's expectations; toggle off ⇒ no
call; feedback store cap.
**Depends on:** 9.4.

---

### Step 9.7 — Retry & robustness polish

**Goal:** the audit's remaining sharp edges.

**How to implement:**

1. `ByokClient`: persist the degraded `reasoning_effort` outcome into
   `ByokCapabilities` on first failure (no per-turn retry storm); parse and
   honor `Retry-After` (cap 30 s) in the retry backoff; per-request
   `timeoutMs` override from profile (long-reasoning models need >120 s).
2. Orchestrator: refresh the project snapshot **per model call** when the
   previous turn executed edits (finishes the staleness fix; the prompt's
   "may be slightly stale" caveat finally becomes rare truth). Snapshot
   fetch failures degrade to the previous snapshot with a chat-visible
   warning line.
3. Rate-limit UX: a `byok-rate-limited` transient banner on the chat while
   backing off (the error row already exists; this only makes it
   non-terminal-looking when a retry is pending).

**Tests:** retry-after honored (fake timers); degraded-effort remembered
(second turn sends none); snapshot refresh condition (edited ⇒ refetched);
timeout override plumbed.
**Depends on:** Phase 5.

---

### Step 9.8 — Dev-only eval harness

**Goal:** measure before/after for every future prompt/skill/tool change.

**How to implement:**

1. `scripts\run-byok-evals.js` + `Byok\evals\`: ~30 tasks in the SOTA
   recommended shape (real-project grounding, multi-tool, verifiable):
   10 event-logic ("coin spawner every 3 s"), 5 layout/spatial ("place 5×5
   grid of X with even spacing" — scored via instance positions), 5
   variables/properties, 5 JS/extension (Phase 8 surface), 5
   perception-repair ("the preview screenshot shows overlapping HUD — fix").
2. Scoring: mechanical where possible (project-diff vs reference, instance
   geometry, test-pass), LLM-as-judge optional (runs on the user's endpoint,
   flagged as such in the report). Output: per-task pass/fail, rounds, tool
   calls, tokens — the four numbers SOTA says to track.
3. Runner lives outside the shipped bundle (script + fixtures excluded from
   the app build; `Byok\evals\` marked dev-only in the build config check).
   Results are markdown reports committed under `REVIEW\evals\` for trend
   tracking.

**Tests:** harness self-check — a trivially-passing and trivially-failing
task both score correctly.
**Depends on:** everything it evaluates (grow the suite as phases land).

---

### Step 9.9 — Phase gate

1. Full gates from `newIDE\app`.
2. Manual QA (recorded): 40+-round build session survives via compaction
   (watch the "Context summarized" row appear and the loop continue);
   restart the app mid-history → chats reload with images; streaming visible
   on a real endpoint + Stop mid-stream keeps partials; two-profile routing
   exercised (network tab shows different models per call kind); benchmark
   run on two models produces a sensible ranking; regression — hosted AI and
   all Phase 5–8 scenarios still green.
3. Prompt version bump only if behavior text changed (`byok-v7`).

## 3. Phase 9 acceptance criteria (phase gate)

- [ ] Streaming works on a real endpoint with graceful fallback and mid-stream Stop (unit + QA).
- [ ] A 40-round session crosses the 0.75 threshold, compacts with the preserved block intact, and completes — no `byok-context-full` unless compaction cannot fit (unit + QA).
- [ ] Chats, images, and archive state survive app restart; quota eviction touches images before transcripts (unit-tested).
- [ ] Routing sends fast/strong profiles per policy; per-chat overrides win; unset advanced fields are omitted (unit-tested).
- [ ] Capability cache eliminates repeated reasoning_effort 400s (unit-tested); benchmark runs and ranks models on the user's machine.
- [ ] Suggestions (opt-in) and local feedback work; nothing is sent to GDevelop servers.
- [ ] Eval harness runs the suite and writes a markdown report under `REVIEW\evals\`.
- [ ] All four checks green; worklog entry complete.
