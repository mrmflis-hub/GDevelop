### [B] BYOK chats become permanently unreachable (no history entry, no way to reselect or stop a backgrounded chat)
- Affected: `AskAiEditorContainer.js` — BYOK selection state (lines 538-547), `onStartOrOpenChat`/`selectAiRequest` (lines 1314-1356, clears `setSelectedByokChatId(null)` at 1323), `confirmLeavingWorkingRequest`/"Continue working" (lines 1514-1564) and `requestClose` (1568-1575); `AskAiHistory.js` (sidebar lists only server `aiRequestSummaries`, lines 341-360); `ByokChatStore.js` — `listByokChats` (73-74) and `archiveByokChat` (80-86) are referenced by **no file outside the store and its spec** (grep over `newIDE\app\src`).
- Explanation: BYOK chat selection lives only in the container's local `selectedByokChatId`. The history sidebar renders only `AiRequestContext` summaries, so a BYOK chat has no entry anywhere. Three realistic flows strand it: (1) the user closes the tab and answers "Continue working" — `requestClose` returns true, the editor unmounts, but the orchestrator keeps running in the background, calling the user's paid endpoint with no UI left to watch or stop it (`onStop` only acts on the selected chat, and the `subscribeByokChats` listener was cleaned up on unmount at lines 548-550); (2) the user opens another chat — `selectAiRequest` nulls the BYOK selection; (3) the project/tab is re-laid-out across a remount — `selectedByokChatId` is plain state, lost with the component while the chat record survives in the module-level store. Phase 4 deliberately deferred *persisted* history, but in-session reachability of a chat the user was just told would "continue working" is broken.
- Proposed solution: list `listByokChats()` in `AskAiHistory` (or a small BYOK section in the sidebar) with `onOpenAiRequest` routed through a new `onStartOrOpenChat` path that sets `setSelectedByokChatId(id)` instead of only server ids; on editor unmount with a working BYOK orchestrator, either suspend it (simplest, defensible: the "keep working" promise is then simply not offered) or keep the store-listening so the chat can be reopened. At minimum, filter the "Continue working" option for BYOK chats in `confirmLeavingWorkingRequest`.
- Tests to write: `ByokSeam.spec.js`-style pure helper + a container-level test is heavy; at minimum a store test that a second subscribe/re-select round-trip (`listByokChats` → `getByokChat`) returns the running chat, plus a manual QA case: start a BYOK chat, close the tab choosing "Continue working", verify the chat is either reachable again or the option is not offered.

### [B] A message sent to a BYOK chat whose orchestrator is missing is silently dropped, and its Retry button is dead
- Affected: `AskAiEditorContainer.js` — `startByokChat` missing-key early return (lines 637-647: the chat record is created and set to error *before* any orchestrator is created), `onSendMessage` BYOK branch (965-986: `orchestrator ? orchestrator.sendUserMessage(...) : Promise.resolve()` — then the input is cleared), `onRetryByokChat` (1495-1504: `if (orchestrator) ...` else silent no-op).
- Explanation: with BYOK enabled+configured but no key stored, `startByokChat` errors out with "No API key is stored for BYOK. Add one in Preferences > BYOK, then send your message again." (line 641-644). Following that instruction — adding the key and sending a message again in the same chat — silently discards the message (no orchestrator exists, the input is cleared, no error is shown). Clicking the error row's Retry (`onRetryByokChat`) also does nothing. The only working recovery is starting a brand-new chat, which the error message does not mention.
- Proposed solution: in the `onSendMessage` BYOK branch, when `byokOrchestratorsRef.current.get(aiRequestId)` is missing, re-create the orchestrator for the existing chat (extract the orchestrator-construction body of `startByokChat` into a reusable `ensureByokOrchestrator(chat)`), or at minimum re-mark the chat with the missing-key error so the user gets feedback. Do the same in `onRetryByokChat`.
- Tests to write: in a new container-level seam test (or an extracted pure helper test): a chat placed in the missing-key error state (no orchestrator) receives `sendUserMessage` → assert the chat either gets a fresh orchestrator call or its error is re-set (assert `updateByokChat` called with `status: 'error'`), never that the message vanishes with no state change.

### [B] The per-model context windows configured in the settings tab have no effect at runtime — the orchestrator only ever uses the global fallback
- Affected: `ByokSettingsTab.js` — per-model rows and writes to `contextWindowByModel` (lines 219-247, 369-396); `ByokModelsCache.js` — `resolveContextWindowTokens` (133-156, fallback chain server → per-model → global → default) is exported but called by nothing at runtime (repo-wide grep: only its definition and spec); `ByokOrchestrator.js` — `contextStatsFromUsage(usage, settings.contextWindowTokens)` (lines 256-263) feeds both the chat's context bar (`AiRequestChat\index.js:510-514`) and the `MAX_BYOK_CONTEXT_RATIO` runaway guard (434-445).
- Explanation: the tab maintains and persists per-model context windows (including "auto (server)" prefills), but the orchestrator computes the context-used ratio against the *global* `contextWindowTokens` (default 8192) for every model. A user who sets 131072 for a large model sees the bar fill ~16x too fast and the loop abort with "conversation is close to the context window limit" long before the real window is full; conversely a small-window model never trips the guard in time. Phase docs (styleguide §1 hard constraint 4) promise "context window (auto-detected from the server when possible, user-set otherwise)".
- Proposed solution: in `createByokOrchestrator`, resolve the window once per chat (or per round) via `resolveContextWindowTokens(settings, getCachedByokModels(connection.baseUrl)?.find(m => m.id === settings.modelName), settings.modelName)` and use that value in `contextStatsFromUsage` and the ratio guard. Keep it injected/derived in a pure helper so it stays testable.
- Tests to write: `ByokOrchestrator.spec.js`: with `settings.contextWindowTokens = 8192`, `contextWindowByModel = { 'big-model': 131072 }` and `modelName = 'big-model'`, a response using 10000 tokens must produce `contextStats.usedPercentage ≈ 0.076`, not ≥ 0.9 (loop must continue). Also a test for the server-reported window taking precedence.

Locale catalogs themselves were not hand-edited (BYOK commits touch 0 files under `src/locales` — verified via `git show --stat`).

### [C] `byok-context-full` leaves the chat in a phantom "working" state, and its Retry re-sends the whole oversized history to the user's endpoint
- Affected: `ByokOrchestrator.js` — context guard placement (434-445: fires right after `recordAssistantTurn`, so the last assistant message has tool calls with **no** outputs) and `retryAfterError` (476-489: only checks `status === 'error'`, re-runs `runLoop` → `callModel` with the full history); `AiRequestChat\index.js` — `hasFunctionsCallsToProcess` treats output-less calls as work (533-538, 554-561) → `isWorking` → send button disabled/turned into Stop; `AskAiEditorContainer.js` — `getHasWorkInProgress` is false for `status === 'error'` (via `AiRequestUtils.js:353-377`), so `onStop` (1476-1491) no-ops; `AiRequestErrorRow.js:51-56` — only `context-too-large` maps to the non-retryable "too-large" presentation, `byok-context-full` is presented as transient with a Retry button.
- Explanation: when the context guard trips, the chat is `error` with pending tool calls: the chat UI shows a working state (disabled input, Stop button) whose Stop does nothing, while the error row simultaneously offers "Try again" — which calls the model again with the entire oversized transcript (a real token charge on the user's endpoint) only to hit the same guard again.
- Proposed solution: (1) before the context-guard `markError`, append not-executed tool outputs (reuse `appendNotExecutedToolOutputs`) so the transcript has no pending calls and the UI settles into a clean error state; (2) make `retryAfterError` refuse on non-retryable codes (`byok-context-full`, `byok-too-many-tool-rounds` is borderline) — or map `byok-context-full` to the server's `context-too-large` code so `AiRequestErrorRow` already hides Retry without touching that file's budget.
- Tests to write: `ByokOrchestrator.spec.js`: drive usage past 0.9 with a tool-call response → assert status `error` **and** every function call has a matching `function_call_output`; assert `retryAfterError()` on a `byok-context-full` chat makes zero client calls.

### [C] BYOK executor's `onObjectsModifiedOutsideEditor` accumulation drops the OR semantics of the server flow
- Affected: `ByokSeam.js:203-206` — `accumulatedObjectsChanges.set(changes.scene, changes.isNewObjectTypeUsed)` (plain overwrite); mirrored upstream logic in `AiGeneration\Utils.js:596-603` — `set(scene, existing || false || changes.isNewObjectTypeUsed)`. The comment at `ByokSeam.js:137-141` claims "the same accumulation the server-backed flow does".
- Explanation: in one batch, if an early call introduces a new object type (`isNewObjectTypeUsed: true`) and a later call in the same scene reports `false`, the flush delivers `false` — the scene editor is not told a new object type was used, and the objects list/type registration may not refresh until the scene is reopened. Edge-case incorrectness that silently diverges from the flow it mirrors.
- Proposed solution: `accumulatedObjectsChanges.set(changes.scene, accumulatedObjectsChanges.get(changes.scene) || false || changes.isNewObjectTypeUsed);` — or an explicit guard-clause helper to keep the no-clever-one-liner rule.
- Tests to write: `ByokSeam.spec.js` (extend the coalescing test at 159-188): call `onObjectsModifiedOutsideEditor({scene:'s', isNewObjectTypeUsed:true})` then `({scene:'s', isNewObjectTypeUsed:false})` → assert the flushed notification has `isNewObjectTypeUsed: true`.

### [C] Context-window number fields clamp on every keystroke, corrupting the value the user is typing
- Affected: `ByokSettingsTab.js` — `clampContextWindow(parseInt(value, 10))` inside `onChange` for the default field (404-415) and the per-model rows (384-393); the clamped integer is immediately re-rendered into the controlled `TextField`.
- Explanation: typing "16384" character by character: '1' → clamped to 512 and the field re-renders as "512"; continuing appends to the rewritten text ("5126" → 5126, "51263" …) and the final keystroke lands on a garbled number, typically ending at 1000000. The user cannot reliably type an intended context-window value; the visible number is not what they typed. The spec masks this by calling `onChange` once with the complete string (`ByokSettingsTab.spec.js:163-193, 447-469`).
- Proposed solution: keep the raw text in local state while the field is focused and clamp/persist on blur (or on `onChange` store the parse but only clamp at commit), mirroring how the API-key field already commits on blur.
- Tests to write: `ByokSettingsTab.spec.js`: simulate successive `onChange` calls ('1', '16', '163', '1638', '16384') and assert the persisted final `setMultipleValues` value is 16384 (currently it would be 1000000); plus a blur-commits-clamp test.

### [C] Settings tab: async handlers set state after unmount, and the desktop save/load key race can use a stale key
- Affected: `ByokSettingsTab.js` — `onFetchModels` (145-171) and `onTestConnection` (173-206) have no mounted guard (unlike the mount effect at 118-131); the blur-save continuation `saveByokKey(apiKey).then(() => setHasStoredKey(...))` (298-300) likewise. Race: `ByokKeyStorage.saveByokKey` on desktop awaits an `ipcRenderer.invoke('byok-encrypt')` round-trip (`ByokKeyStorage.js:139-146`) before writing, while the button's `await loadByokKey()` reads `localStorage` synchronously at click time (`ByokKeyStorage.js:222-227`).
- Explanation: (1) Closing the Preferences dialog while a models fetch or connection test is in flight updates state on an unmounted component. (2) On the desktop build (the primary target per styleguide §1), the natural flow "type key → immediately click Fetch models/Test connection" blurs the field (save dispatched, IPC in flight) and then reads the *old or empty* stored key, producing a misleading 401/"network" error for a key that was just typed. On web the write lands in a microtask before the click task, so it only shows on desktop.
- Proposed solution: thread an `isSubscribed` ref (or a mounted flag) through both handlers exactly like the mount effect; for the race, make the button handlers use the in-flight save: keep a promise of the last `saveByokKey` and `await` it before `loadByokKey`, or save the key synchronously enough (e.g. have `onFetchModels`/`onTestConnection` call `await savePendingKeyFirst()`).
- Tests to write: `ByokSettingsTab.spec.js`: unmount the renderer inside `onFetchModels` (reject/resolve after unmount) and assert no "state update on unmounted component" behavior (wrap in act and assert no throw/log); a test where `saveByokKey` is slow (deferred promise) and the fetch button is clicked — assert `refreshByokModels` receives the newly typed key, not `''`.

### [D] No explicit "Clear key" action; storage-status row can claim a key is stored after a failed save
- Affected: `ByokSettingsTab.js` — the only clearing path is emptying the field and blurring (works: `saveByokKey('')` clears, `ByokKeyStorage.js:192-196`), but nothing in the UI communicates it; `onBlur` sets `setHasStoredKey(!!apiKey)` unconditionally after `saveByokKey` resolves (298-300) even though a storage failure is swallowed as `console.error` (`ByokKeyStorage.js:212-214`), so the status row then asserts a key exists when none was written. - Explanation: users wanting to remove a key (e.g. before sharing the machine) have to guess the empty-and-blur gesture; and after a quota-full/corrupted localStorage the UI lies about storage state.

- Tests to write: `ByokSettingsTab.spec.js`: clicking the clear button removes `gd-byok-key` from localStorage, empties the field state and hides the status row; a save failure keeps `hasStoredKey` false.
